00 · Brief

How to use this document

This isn't generic tutorial content — every trace below points at real files in this exact repo. The goal isn't to memorize these thirteen sections; it's to walk out able to do the same trace on any file a reviewer points at, including ones not covered here.

The two-question method

When someone points at a line of code and asks "what is this, and where does it come from," you're really answering two separate questions:

  1. What is its type/shape? Check the Zod schema right above it, the TypeScript interface, or the Prisma model. Say it out loud: "this is an object with an employeeId string and a checkIn date."
  2. What is its concrete source, for one real call? Not "req.body is the request body" (true but says nothing) — trace it to the exact line upstream that built it. Section 02 does this for one real endpoint, start to finish.

Finding any route yourself, in under a minute

  • frontend/src/api/*.ts

    Grep for the resource name (e.g. "contract") — every backend call in this app goes through one of these files, each wrapping a single apiClient.get/post/put/delete call.

  • docs/02_API_CONTRACTS.md

    Confirms the exact method, path, and expected shape — the contract both sides were built against.

  • backend/src/routes/index.ts

    Shows which module router owns that URL prefix.

  • backend/src/modules/<name>/*.routes.ts → *.controller.ts → *.service.ts

    Same three-file shape every time: routes wire middleware, controller validates input, service holds the actual logic and talks to Prisma.

    • 01 · General pattern

    The request lifecycle, in general

    Every single API call in this app — Employees, Attendance, Payroll, all of it — follows the same six-stop shape. Learn this once.

    Two stops are worth calling out because they're where reviewers probe hardest:

    • The middleware chain runs in the exact order it's registered in app.ts, every time, no exceptions — express.json() must run before any route that reads req.body, or req.body is simply undefined.
    • Controller vs service is a deliberate split: the controller's only job is "parse input, call one service function, shape the response" — zero business logic. The service is where every rule this app enforces actually lives (RBAC checks, the contract-overlap rule, the payroll math). If asked "where would you add a new validation rule," the answer is almost always the service, not the controller.

    03 · Pipeline

    Middleware

    A middleware is a function shaped (req, res, next) => {} that sits between "request received" and "your route handler runs." It can read or mutate req/res, end the request early, or call next() to let the next one run. Express executes them in exactly the order they're registered — never out of order, never in parallel.

    ScopeRegisteredOur example
    Globalapp.use(x) in app.tshelmet(), cors(), express.json() — runs on every request
    Router-levelrouter.use(x)attendanceRouter.use(authenticate) — every attendance route
    Route-specific2nd arg to .post()requireRole(...HRM_PLUS) on one single route
    Error-handlinglast, 4-arg signatureerrorHandler — only runs when something calls next(err)

    General use cases beyond auth: request logging, rate limiting, response compression, CORS, input sanitization — anything you'd otherwise have to repeat inside every single controller.

    04 · The distinction they always ask

    Authentication vs. authorization

    Authentication — who are you

    Proving identity. Our login endpoint compares a bcrypt hash, then signs a JWT containing {'{'}userId, employeeId, roles{'}'}. Every later request proves identity by presenting that token; authenticate middleware verifies it and attaches req.auth.

    Authorization — what are you allowed to do

    Deciding if this specific action, on this specific data, is permitted for an already-proven identity. Two layers here: coarse role gates (requireRole(...)) and finer service-level checks (an Employee can only view their own attendance — that can't be expressed as "does this role exist," it needs the actual data).

    One-liner

    Authentication is the same check on every request. Authorization can change per action and per row of data — that's why some of it lives in route middleware and some of it has to live inside the service.

    05 · Async control flow

    Promises and async/await

    A Promise represents a value that will exist later — pending, then either fulfilled or rejected, exactly once. .then(onOk, onErr) schedules callbacks for whichever happens; .catch(fn) is shorthand for .then(undefined, fn).

    Chaining — the "trailing" part

    Each .then() returns a new promise, so a chain runs in strict order, and a single trailing .catch() catches a rejection from any earlier link:

    chaining, illustrative
    fetchUser(id)
  .then(user => fetchRoles(user))   // only runs if fetchUser resolved
  .then(roles => render(roles))     // only runs if fetchRoles resolved
  .catch(err => showError(err));    // catches a rejection from EITHER step above

    async/await is the same thing, different syntax

    await pauses only the current async function (not the whole thread — other requests keep being handled) until a promise settles, then either hands back the value or throws the rejection as a normal exception you can try/catch.

    asyncHandler.ts — why it exists
    // Express 4 does NOT forward a rejected promise from an async route handler
// to error middleware on its own. Without this wrapper, a thrown error
// inside an async controller hangs the request instead of reaching errorHandler.
export function asyncHandler(handler) {
  return (req, res, next) => { handler(req, res, next).catch(next); };
}

    Also used constantly: Promise.all([...]) — e.g. getEmployeeById fetches the four smart-button counts (contracts/attendance/time-off/payslips) concurrently instead of four sequential round-trips.

    06 · Runtime model

    Is Node.js single-threaded?

    Yes — one call stack, one thing executing JS at a time. But Node (via libuv) also runs an event loop plus a small background thread pool for work that would otherwise block: file I/O, DNS, and CPU-heavy crypto. Network I/O — our Postgres queries — doesn't even need the thread pool; the OS handles it asynchronously and delivers the result back to the single JS thread as a callback when ready.

    Why this is a deliberate design, not a limitation

    An API server like this one spends almost all its time waiting — on the database, on the network — not computing. A single-threaded event loop skips the cost and the bug-class (races, locks, deadlocks) of thread synchronization for all that waiting time: while one request awaits its Prisma query, the loop is free to start the next request immediately.

    Concrete spot in this codebase

    bcrypt.compare() in auth.service.ts is deliberately slow (that's what makes it secure) and CPU-bound — the async bcrypt API pushes that work off the main JS thread via libuv's pool, so one login attempt hashing a password doesn't stall every other request on the server.

    07 · Type system

    Why TypeScript

    TypeScript adds static types checked at compile time (tsc), then erases them entirely — the output is plain JavaScript with zero runtime cost or behavior difference.

    • Catches bugs before they run: a wrong argument type or a typo'd property name is a red squiggle at write-time, not a silent undefined during a judged demo.
    • Safe refactors: rename a Prisma field, and every call site that breaks lights up immediately — no grepping and hoping.
    • The schema becomes the types: Prisma generates a fully-typed client straight from schema.prisma, so the database shape and the code's types can never quietly drift apart.

    Why here specifically: RBAC logic and payroll math are exactly the kind of code where a misread field name is expensive — TypeScript catches that class of mistake at build time. More broadly, it earns its keep on any codebase touched by more than one person, or with a contract shared between two sides (our docs/02_API_CONTRACTS.md field names are enforced as real types, not just documentation someone can forget to update).

    08 · Component data flow

    React Context and prop drilling

    The problem, concretely: Parent(name) → Child1(name) → Child2(name) → Child3(name) — if only Child3 actually uses name, Child1 and Child2 still have to accept and forward it purely as a relay.

    Drawbacks of the chain

    • Every intermediate component's props are polluted with data it never reads itself.
    • Renaming or removing that value means touching every file in the chain, not just the one that needs it.
    • Forgetting to forward it at one link silently produces undefined three components later — a hard bug to trace.
    • Intermediate components become harder to reuse elsewhere, since they now require props unrelated to what they actually do.

    How Context fixes it — our real example

    AuthContext.tsx puts user, token, and hasRole() on a Provider once, near the top of the tree. The Sidebar, TopHeader, every page's route guard, and deep-nested action buttons each call useAuth() directly — none of them received user as a prop from their parent.

    The trade-off, if pushed on it

    Context isn't free: every consumer re-renders when the context value changes. That's fine for something that changes rarely (the logged-in user) and a bad fit for something that changes on every keystroke — which is exactly why this app has two small, infrequently-changing contexts (AuthContext, ToastContext) rather than one giant context holding everything.

    09 · Dependency management

    package.json vs. package-lock.json

    package.json

    Hand-authored manifest: project metadata, the scripts you run (npm run dev), and dependencies as version ranges — ^5.20.0 means "5.20.0 or any newer compatible 5.x.x."

    package-lock.json

    Auto-generated. Pins the exact resolved version of every dependency — direct and transitive — plus integrity hashes, at the moment it was installed.

    The reason both exist: two machines running npm install against the same package.json, weeks apart, could legally resolve different patch versions within the same range. The lockfile makes that installation reproducible byte-for-byte instead. Commit both, always; never hand-edit the lockfile; npm ci (used in CI/production) installs strictly from the lockfile and fails loudly if it's out of sync, where plain npm install would just quietly update it.

    10 · Distributed systems

    CAP theorem

    In a distributed data system, once a network Partition (P) happens — and eventually one will — you can keep only one of Consistency (every read reflects the latest write, or errors) or Availability (every request gets a response, possibly stale). Not both, during that partition. Outside of a partition, you can have both.

    Where this actually binds us: a single Postgres instance and a single backend process isn't a distributed system yet, so CAP doesn't constrain this build today. It becomes the live question the moment you add a read replica, shard the database, or run multiple backend instances behind a load balancer.

    If asked "which would PeoplePay360 pick"

    Payroll leans CP (consistency over availability): a payslip computation briefly failing is far better than silently under- or over-paying someone from stale data. Contrast with something like a social feed, which reasonably leans AP — showing slightly stale content beats an error page.

    11 · From scratch

    SQL: users, roles, and assignments

    The exact shape of our real users / roles / user_roles tables — a classic many-to-many via a junction table — written as plain SQL.

    schema
    CREATE TABLE roles (
  id   SERIAL PRIMARY KEY,
  name VARCHAR(50) UNIQUE NOT NULL          -- 'ADMIN', 'HR_MANAGER', ...
);

CREATE TABLE users (
  id            SERIAL PRIMARY KEY,
  name          VARCHAR(120) NOT NULL,
  email         VARCHAR(255) UNIQUE NOT NULL,
  password_hash TEXT NOT NULL
);

-- junction table: one user can hold many roles, one role can belong to many users
CREATE TABLE user_roles (
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  role_id INTEGER NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
  PRIMARY KEY (user_id, role_id)
);

    SELECT u.id, u.name, u.email, r.name AS role_name

    12 · Nerves check

    Rapid-fire answers

    QuestionOne-line answer
    What does express.json() do?Parses a JSON request body into req.body. Without it, req.body is undefined.
    Where does req.auth come from?Set by the authenticate middleware after verifying the JWT — not part of the raw HTTP request.
    Why does asyncHandler exist?Express 4 won't auto-forward a rejected promise from an async handler to error middleware.
    401 vs 403?401 = not authenticated (missing/invalid token). 403 = authenticated, but not allowed to do this.
    Why UUID primary keys, not auto-increment ints?A team decision to avoid rippling type changes through code already written against string ids — a trade-off, not a universal rule.
    Two requests race to create the same payslip — what stops a duplicate?A DB-level UNIQUE(payrunId, employeeId) constraint — enforced by Postgres itself, not application code.
    Why is validation in the service, not just the controller?The controller only checks shape (Zod). Business rules — like "no overlapping contracts" — need a database lookup, which belongs in the service.
    What's a race condition, and where could one bite us?Two operations reading-then-writing shared state without isolation. Payroll validation guards against it with a DB CHECK (maker ≠ checker) plus a transaction.

    This document is a floor, not a ceiling — the real test next review is whether you can do the section 02 trace live, on a file nobody prepped. Practice it on one more endpoint you didn't pick tonight.

    13 · Failure paths

    Error & exception handling

    The rule this codebase follows: every failure becomes a typed, predictable object — never a raw stack trace to a client, never a silently swallowed error, never a hung request.

    Backend: three layers

    LayerTechniqueWhere
    Input shapeZod schema .parse() throws ZodError on anything malformedEvery controller, before touching the service
    Business rulesServices throw a typed ApiError (badRequest, conflict, forbidden, notFound) with a specific status + human message*.service.ts — e.g. contract overlap → ApiError.conflict(...)
    Data integrityPostgres itself rejects the write (UNIQUE, CHECK, exclusion constraints) if application logic somehow missed itDB constraints — the last line of defense, not the first
    errorHandler.ts — the single place that turns any of the above into a response
    export function errorHandler(err, _req, res, _next) {
  if (err instanceof ApiError) {
    return res.status(err.statusCode).json({ success: false, error: err.message });
  }
  if (err instanceof ZodError) {
    const first = err.issues[0];
    return res.status(422).json({ success: false, error: `${first.path.join('.')}: ${first.message}` });
  }
  console.error(err); // anything truly unexpected still gets logged server-side
  return res.status(500).json({ success: false, error: "internal: unexpected server error" });
}

    Everything reaches this one function because every async controller is wrapped by asyncHandler (section 05) — a thrown ApiError, a thrown ZodError, or a genuinely unexpected exception all funnel to the exact same place, so the response shape is never inconsistent depending on which layer failed.

    Frontend: normalize once, at the boundary

    client.ts's axios response interceptor reads the backend's {'{'}success:false, error{'}'} envelope (or maps a bare HTTP status like 401/403/409 to a plain-language message when the backend didn't get a chance to respond at all) and re-throws a single normalized Error — so every calling component just does one try/catch and shows err.message, never branching on response shape itself.

    The distinction worth stating precisely

    Validation error (Zod, 422) = the request itself is malformed — wrong type, missing field. Business rule error (ApiError, 409/403/400) = the request is well-formed but violates a rule that requires knowing the current data — an overlapping contract, insufficient leave balance. Exception (500) = something nobody anticipated — a bug, a DB connection drop. Only the last category should ever reach a bare catch with a generic message; the first two should always be specific and actionable.

    14 · Growth

    Horizontal vs. vertical scaling

    Vertical — a bigger machine

    Give the existing single server more CPU/RAM/disk. Simple, no code changes, but has a hard ceiling (there's a biggest machine money can buy) and it's a single point of failure — that one box going down takes everything with it.

    Horizontal — more machines

    Run multiple copies of the app behind a load balancer, splitting traffic across them. No hard ceiling, survives one instance dying, but requires the app to not depend on any one instance's local memory.

    Where this app already scales horizontally for free — and why

    Our auth is a stateless JWT — the server holds no session data in memory; every request carries everything needed to verify identity in the token itself. That means any of N identical Express instances can handle any request with zero "sticky session" requirement — a load balancer could round-robin across them today with no code change. This was the actual reason to choose JWT over server-side sessions, not just convention.

    Where it wouldn't scale yet, and what would have to change

    • The database is the real bottleneck. One Postgres instance, one connection pool. Horizontal scaling of the Express layer doesn't help if 50 instances are all hammering the same single DB. The DB itself scales vertically first (bigger instance), then via read replicas (route GETs to replicas, keep writes on the primary) — which is exactly where CAP theorem (section 10) stops being theoretical: a replica can lag behind the primary by milliseconds, so a read right after a write might not reflect it yet.
    • The payroll compute loop (section 02-adjacent: payrun.service.ts's computePayrun) currently processes payslips in a loop within one request. At real scale (thousands of employees per payrun) that would move to a background job queue instead of blocking one HTTP request — the API would return immediately with "processing," and a worker pool (which itself scales horizontally, independently of the web tier) would do the actual computation.
    • File-based things (the PDF generation) are fine stateless today since nothing is written to local disk — the PDF is generated in memory and streamed straight to the response. That's deliberate: it means any instance can serve that request, with no shared-filesystem requirement to solve later.
    If asked "how would you scale this to 10,000 companies"

    Horizontally scale the stateless Express layer behind a load balancer (free, given the JWT choice already made) → add a Postgres read replica for the read-heavy Dashboard queries → move payroll compute to a background job queue → only then consider vertical scaling or sharding the database itself, since that's the expensive, hard-to-reverse step.

    15 · Postmortem

    Incident log: the silent backend crash

    A real incident from this build, worth being able to narrate — "walk me through a bug you debugged" is a favorite review question, and this one is genuine, not rehearsed.

  • Symptom

    Frontend appeared to make no visible progress against the live backend during a review; a reviewer checking DevTools' Network tab reported seeing nothing meaningful.

  • First hypothesis (rejected)

    Assumed a frontend bug — a request never being fired. Ruled out by grepping the codebase for any page bypassing the API layer to render mock data directly: none existed. The API layer always attempts a real network call first.

  • Investigation

    curl http://localhost:4000/health returned nothing — connection refused. The backend process itself was gone, even though nobody had intentionally stopped it.

  • Root cause, found in the server's own log

    The dev server runs under ts-node-dev --respawn (auto-restart on file change). A file on disk changed (a git operation touching a backend file counts, same as an editor save), triggering a restart — and the respawn silently failed to rebind port 4000, most likely a port-release race condition on Windows. No crash message reached anyone because it was running as an unattended background process.

  • Fix

    Restarted the process manually for continued development. For anything actually presented live, switched the recommendation to npm run build && npm start — the compiled server has no file-watcher and nothing to silently fail a restart on.

  • Prevention

    Always verify both servers respond immediately before presenting (curl the health endpoint, or just load the page) — "it worked earlier" is not evidence it works now. A background dev process is a development convenience, not a demo-time guarantee.

    • 16 · Two quick vocabulary pairs

    require vs. import, resolve vs. reject

    Covering both, since either could be what was actually asked.

    require() vs import

    require() is CommonJS — Node's original module system. It's synchronous: the whole required file runs to completion before the line after require() executes. import is the ES Module standard (native to modern JS, including the browser) — it's statically analyzable (tooling can see your dependency graph without running the code) and supports asynchronous loading. Our backend's tsconfig.json targets commonjs (that's what ts-node/Node running directly compiles down to), but we write import syntax throughout — TypeScript transpiles our import statements into require() calls under the hood before Node ever sees them. The frontend (bundled by Vite) uses real native ES Modules, no transpilation to CommonJS needed, since browsers and modern build tools support import directly.

    resolve vs. reject

    The two functions a Promise's executor receives: new Promise((resolve, reject) => {'{'} ... {'}'}). Calling resolve(value) fulfills the promise — anything chained with .then() runs next. Calling reject(error) fails it — control jumps to the nearest .catch() (or the catch block of a surrounding try/await). In our own code we rarely construct a new Promise by hand — async functions do this implicitly: a return value is an automatic resolve, a throw err is an automatic reject. That's precisely why throw ApiError.conflict(...) inside an async service function behaves like a rejected promise, which is exactly what asyncHandler's .catch(next) is there to catch (section 05).

    17 · List responses at scale

    Pagination — backend and UI

    Why it exists: returning every row of a large table in one response is slow, wastes bandwidth, and doesn't scale — pagination splits a large result set into pages the client asks for one at a time.

    Two backend techniques

    TechniqueHowTrade-off
    Offset/limit?page=2&limit=20 → SQL LIMIT 20 OFFSET 20 (Prisma: take: 20, skip: 20)Simple, supports jumping to any page number — but slow on very large tables (the DB still has to scan past all skipped rows), and a row inserted mid-list can shift results between page loads
    Cursor-based?after=<last_seen_id>&limit=20 → WHERE id > last_seen_id ORDER BY id LIMIT 20Fast at any depth, stable under concurrent inserts — but can't jump to an arbitrary page number, only "next"

    UI side

    The frontend needs: current page state, a way to request the next/previous page (numbered page buttons, "Load more", or infinite scroll firing the next request as the user nears the bottom), and a total count or a "there's more" flag from the backend to know whether to keep showing a "next" control.

    Honest answer if pushed on our code specifically

    This API doesn't paginate yet — GET /api/employees, /attendance, and every other list endpoint return every matching row in one response. That's a real, known gap, acceptable for the seed-data scale of a hackathon demo (dozens of rows) but the first thing that would need adding before this handled a company with thousands of employees. The fix is mechanical: add page/limit query params to each list endpoint's Zod-validated query schema, pass them to Prisma as skip/take, and return a small envelope like {'{'} data: [...], total: 400, page: 2, pageSize: 20 {'}'} instead of a bare array.

    18 · The actual skill, not a feature

    Debugging, properly

    Correcting something directly: debugging is not "write a function that does the debugging." A logging function is one possible tool you might use while debugging — debugging itself is the process of comparing what the program actually does against what you expected, narrowing down exactly where those two diverge, using whatever tool answers that fastest.

    The real toolbox, cheapest to most powerful

  • Read the error, fully, top to bottom

    A stack trace lists every function call that led to the crash. Find the first line that's your code, not a library's — that's almost always where the real problem lives, even if the crash happened three library-internal frames later.

  • Strategic console.log

    Fast and ubiquitous, but manual: log the input and output of a suspect function, re-run, read the actual values, compare against what you expected. This is the "add a logging function" instinct — fine as one tactic, just not the whole answer.

  • A real debugger with breakpoints

    Far more powerful: pause execution at an exact line and inspect everything live — every variable in scope, the full call stack, without editing the code at all. For our backend:

    package.json — add a debug script
    "dev:debug": "ts-node-dev --inspect --respawn --transpile-only src/server.ts"

    Run it, then either open chrome://inspect in Chrome and click "inspect," or in VS Code use "Attach to Node Process." Click the gutter left of a line (e.g. const body = checkInSchema.parse(req.body) in attendance.controller.ts) to set a breakpoint, trigger that request from the frontend or Postman, and execution pauses exactly there — req.body, req.auth, every local variable is inspectable in the Variables panel, and you can step line-by-line (Step Over/Into/Out) to watch the trace from section 02 happen in real time instead of reading it as prose.

  • React DevTools (frontend)

    The Components tab shows the live component tree with each component's current props, state, and context values — the direct way to answer "why did AttendancePage render with the wrong data," without adding a single console.log.

  • The Network tab

    For "is the bug in my code, or in what the server sent me" — inspect the actual request payload and response body for one specific call, which is also exactly how the earlier network-tab investigation (section 15) got solved.

  • git bisect

    For "this used to work" bugs: binary-searches your commit history, running your reproduction step at each candidate commit, to find the exact commit that introduced a regression — far faster than manually checking out commits one at a time.

    • If asked to debug a specific function live

    Narrate the method, don't just stare at the code: "First I'd read the error/stack trace to find where it actually throws. Then I'd set a breakpoint right before that line and inspect the real values of its inputs — if they're not what I expected, the bug is upstream of here, so I'd move the breakpoint back one call in the trace and repeat, until the actual value and the expected value diverge for the first time. That's the line the bug is on." That's the whole method — bisecting a call chain by inspecting real state, not adding a special "debug function."
